⏺ I've read the paper, the axiom code, and mapped both against Cortex's actual
  state-management internals. Here's my assessment.

  TL;DR

  The paper's valuable export for Cortex is not the database engine — it's the
  schema discipline: treat everything your agents do (attempts, gate results,
  fixes, retries) as a persistent, queryable graph with lineage and fitness
  scores, instead of scattered files and post-hoc transcript scraping. Cortex
  already has ~70% of the raw ingredients (WAL, temporal.db, pipeline_handoff,
  script-capture, the analyze pipeline) but they're disconnected silos. Unifying
  them into one experience store would directly improve pipeline crash
  recovery, cross-session reuse, and the quality of /cortex/analyze output.
  Axiom itself (the code you downloaded) is not worth adopting — more on that
  below.

  What the paper actually says

  Trellis stores the agent's entire search history as database state in a
  four-level hierarchy: tasks (spec + success metric) → sessions (who is
  searching, with what algorithm, how far) → nodes (parent link, artifacts,
  execution output, fitness score, evidence) → prompt histories (exact messages
  the LLM saw at each step). Three mechanisms make it powerful:

  1. Recovery is a query, not a checkpoint. Agents hold no irreplaceable state;
  a dead worker loses at most one step, and any worker resumes from the last
  committed node.
  2. Cross-session reuse via vector-seeded graph retrieval. New task → embed
  description → find similar prior tasks → walk relational links to their
  highest-fitness, non-buggy nodes. This is where the reported 10× speedup / 52%
  token savings came from: not repeating past mistakes.
  3. Training/learning data becomes queries. SFT trajectories are root-to-leaf
  paths; preference pairs are sibling nodes under the same parent where one
  scored higher — "a graph pattern match, not a post-hoc log scrape." A
  step-numbered change log allows AS-OF reconstruction of what the agent knew at
  any point, preventing future-information leaks.

  About axiom-main: it contains no agent or experience-graph code at all. It's a
  C++20 Velox-based SQL engine (Presto parser, cost-based optimizer,
  distributed runner) — the query substrate Trellis runs on at Meta scale. For a
  local-first Python MCP server, adopting it would be a massive dependency for
  zero benefit. SQLite (which Cortex already ships as temporal.db) plus an
  embedding index is the right scale. Take the schema, skip the engine.

  Mapping to what Cortex already has

  Trellis concept: Node change log (step-numbered)

  Gap: Records only hashes + byte deltas — can't reconstruct content, no AS-OF
  ────────────────────────────────────────
  Trellis concept: Temporal facts
  Cortex today: temporal.db (SPO triples, valid_from/valid_to)
  Gap: Not linked to sessions/attempts that produced the facts
  ────────────────────────────────────────
  Trellis concept: Session/phase state
  Cortex today: pipeline_handoff (JSON files per phase)
  Gap: Has snapshot/rollback, but no lineage, no fitness, cleared per-session —
  experience is discarded
  ────────────────────────────────────────

  Gap: Consumed once, then thrown away
  ────────────────────────────────────────

  ────────────────────────────────────────

  Gap: Exactly the fragile post-hoc log scraping the paper argues against
  ────────────────────────────────────────
  Trellis concept: Skills
  Cortex today: Synapse prompts/rules + quality gate as success metric
  Gap: Already matches the paper's "skill" model well — this part is validated,
  not missing

  What I'd actually build (prioritized)

  1. Unified experience store in SQLite (highest leverage, modest effort).
  Extend temporal.db (or a sibling experience.db) with the paper's schema:
  tasks, sessions, nodes(id, parent_id, session_id, artifact_ref, fitness, 
  status, step_number). Every pipeline phase (commit-phase-a, fix-quality
  iteration, implement-code subtask) writes a node; each run_quality_gate()
  result becomes that node's fitness. Large artifacts (gate logs, diffs) stay on
  disk, linked by reference — same pattern the paper uses with object storage.

  2. Pipeline resume as a frontier query. Right now a crashed /cortex/commit or
  /cortex/fix run restarts from scratch (or from a manually-read handoff file).
  With nodes + status in the store, resume becomes "select the last committed
  node for this session and continue" — the paper's headline reliability win,
  and it maps cleanly onto your existing snapshot/rollback/mark_running
  operations, which are already halfway there.

  3. Vector-seeded recall in session() / load_context. Add task-description
  embeddings alongside BM25. When a new fix/implement session starts, retrieve
  similar prior tasks and surface their highest-fitness outcomes ("last time
  this pyright error class appeared, the fix that passed the gate was X") and
  their dead ends ("autofix loop on markdown lint failed 3× via approach Y").
  This is the single mechanism behind the paper's 52% token reduction, and it
  composes with your existing progressive_loader budget logic.

  4. Rewire /cortex/analyze from scraping to querying. With attempts stored as
  sibling nodes, the analyze pipeline's mistake-pattern detection becomes the
  paper's DPO query: siblings under the same parent where one passed the gate 
  and one failed are natural before/after pairs. Those pairs feed directly into
  failure_based_evals.json and Synapse rule recommendations with evidence
  attached, instead of being re-inferred from transcripts each time. This
  strengthens the whole Compound step of your Plan→Work→Review→Compound loop.

  5. (Optional) Content-preserving WAL for AS-OF reconstruction. Store deltas,
  not just hashes, keyed by step number. Enables "what did the memory bank say
  when the agent made this decision" — useful for honest post-mortems and for
  debugging memory-bank drift. Cheapest to defer; only worth it if 4 proves
  valuable.

  One Synapse-specific idea beyond the paper: Synapse already distills
  experience across projects as rules/prompts. An experience store gives that
  distillation provenance — each rule recommendation could cite the node pairs
  (failure → fix) that justify it, and rules that stop matching real failures
  become candidates for pruning. That closes the self-improving loop the paper
  describes, at dev-tool scale rather than RL-training scale.

  If you want to move on this, the natural next step is a /cortex/plan session
  for item 1+2 (they're one schema change plus pipeline_handoff
  instrumentation); 3 and 4 layer on top independently.
