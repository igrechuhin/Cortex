# Structured Plan Creation via Cortex MCP Tools

**Status**: Pending  
**Created**: 2026-02-01  
**Source**: User request + transcript `bbcc3cd2-80f0-408d-9da0-f70ee3775904` (create-plan pipeline)

## Goal

Replace the current **manual** plan-creation flow (agent writes the plan file with the Write tool and updates the roadmap by passing full roadmap content to `manage_file`) with a **structured, tool-driven** flow using dedicated Cortex MCP tools. This makes plan creation consistent, auditable, and less error-prone (e.g. no accidental truncation of roadmap, no path hardcoding).

## Context

### Current Behavior

When the create-plan pipeline is invoked (e.g. via `user-cortex/plan`):

1. **Plan file**: The agent uses **standard Write tool** to create or update the plan file in the plans directory. Path comes from `get_structure_info()` → `structure_info.paths.plans`; content is generated by the agent and written in one shot.
2. **Roadmap**: The agent uses **`manage_file(file_name="roadmap.md", operation="write", content=<full roadmap text>)`** to register the plan. The agent must read the full roadmap, insert or update one entry in the correct section/order, and pass the **entire** resulting content. Phase 66 already enforces that roadmap updates go only through `manage_file` (no StrReplace/direct Write).

### Problems

- **Manual and brittle**: Plan file creation is a raw file write; there is no structured API for "create plan" or "register plan in roadmap." Agents must remember path resolution, section order, and full-content semantics.
- **Roadmap merge is manual**: The agent edits the full roadmap text (string manipulation) to add one bullet; mistakes can truncate or corrupt other entries (Phase 63/66 addressed this with strict rules and verification).
- **No single source of truth for plan schema**: Plan structure (title, status, goal, steps, etc.) is only in the create-plan prompt; tools could enforce it.

### Desired State

- **Structured plan creation**: A Cortex MCP tool (e.g. `create_plan` or `write_plan`) that accepts structured inputs (title, slug/filename, content or sections) and writes the plan file under the plans directory (path resolved inside the tool). Optional: validation of required sections, versioning.
- **Structured roadmap registration**: A Cortex MCP tool (e.g. `register_plan_in_roadmap`) that accepts structured inputs (plan title, short description, status, section name or position) and updates `roadmap.md` by **merging** the new entry into the correct place without the agent handling full content. Implementation still uses memory-bank semantics (e.g. via existing services and `manage_file` under the hood) but exposes a narrow API so the agent never constructs or passes full roadmap text.
- **Promotion**: Update the create-plan prompt (and any Synapse agents) to **prefer** these tools over manual Write + full roadmap write. Keep `get_structure_info` and `manage_file` as fallbacks or for other memory-bank operations.

## Approach

1. **Design** the tool contracts: parameters, return shapes, and behavior for `create_plan` and `register_plan_in_roadmap` (and optionally `list_plans` / `get_plan` for discovery).
2. **Implement** the tools in Cortex (thin handlers + pure helpers; path resolution via existing structure/memory-bank services).
3. **Integrate** with memory bank: `register_plan_in_roadmap` should perform a read-modify-write of `roadmap.md` via existing `manage_file` or equivalent so versioning and conflict detection are preserved.
4. **Update prompts**: Create-plan prompt (and memory-bank-updater if used) should instruct agents to use the new tools first; document fallback to current flow if tools are unavailable.
5. **Test**: Unit tests for helpers; integration tests for tool behavior and for create-plan flow using the new tools.

## Implementation Steps

### Step 1: Define Tool Contracts and Types (High)

- **Target**: Design doc or in-code TypedDicts/protocols for:
  - `create_plan`: e.g. `title`, `slug` (optional, derived from title if missing), `content` (full markdown) or `sections` (structured key-value). Returns: path, success, error message.
  - `register_plan_in_roadmap`: e.g. `plan_title`, `description` (one-line or short bullet), `status` (PENDING | COMPLETE | etc.), `section` (e.g. "Pending plans" or "Blockers") or `position` (after which entry). Returns: success, error message. Tool must read current roadmap, insert/update entry in correct place, write full content via existing memory-bank write path.
- **Output**: Document in plan or in `docs/api/tools.md`; add TypedDicts in Cortex codebase for request/response.

### Step 2: Implement `create_plan` MCP Tool (High)

- **Target**: New or existing Cortex tool module (e.g. `src/cortex/tools/plan_operations.py` or under structure).
- **Behavior**: Resolve plans directory via `get_structure_info()` (or internal structure manager); sanitize slug/filename; write plan content to `{plans_dir}/{slug}.md`; optional validation of required headings (e.g. Goal, Implementation Steps). Use existing file I/O and path validation (no traversal).
- **Handler**: Thin async handler with `@mcp.tool()` and `@mcp_tool_wrapper(timeout=...)`; delegate to pure helper for path resolution and file write.
- **Tests**: Unit tests for helper (path resolution, slug sanitization, write); integration or tool test that calls `create_plan` and verifies file exists and content matches.

### Step 3: Implement `register_plan_in_roadmap` MCP Tool (High)

- **Target**: Same or adjacent module; uses memory-bank (roadmap) read/write.
- **Behavior**: Read `roadmap.md` via existing `manage_file(file_name="roadmap.md", operation="read")` (or internal equivalent); parse sections (Blockers, Active Work, Future Enhancements, Pending plans); insert or update one bullet for the plan in the requested section/position; write full content via `manage_file(file_name="roadmap.md", operation="write", content=..., change_description=...)`. Preserve all existing entries; no truncation.
- **Handler**: Thin async handler; delegate to pure helper for parse-merge-format. Ensure roadmap format (markdown list items, section headers) is preserved.
- **Tests**: Unit tests for merge logic (insert new entry, update existing, section order); integration test that calls tool and then reads roadmap to verify entry present and rest unchanged.

### Step 4: Optional — `list_plans` and `get_plan` (Medium)

- **Target**: Discovery and reuse. `list_plans`: return list of plan filenames or titles in plans directory (exclude archive if desired). `get_plan`: read plan by slug/filename, return content or metadata. Enables "check for similar plan" and "enrich existing plan" without raw file reads.
- **Tests**: Unit tests for list/get; optional integration with create-plan flow (e.g. "list before create" to avoid duplicates).

### Step 5: Update Create-Plan Prompt and Documentation (High)

- **Target**: `.cortex/synapse/prompts/create-plan.md` (and any Synapse agents: plan-creator, memory-bank-updater).
- **Change**: In Step 5 (Create or Enrich the Plan) and Step 6 (Register Plan in Roadmap), instruct agents to use `create_plan` and `register_plan_in_roadmap` when available. Steps become: (1) Generate plan content; (2) Call `create_plan(title=..., content=...)`; (3) Call `register_plan_in_roadmap(plan_title=..., description=..., status=PENDING, section="Pending plans")`. Retain fallback: if tools are unavailable or fail, use current flow (Write to `structure_info.paths.plans` and `manage_file(roadmap.md, write, full content)`).
- **Documentation**: Update `docs/api/tools.md` and CLAUDE.md with new tools (USE WHEN, EXAMPLES, RETURNS).

### Step 6: Integration Tests for Create-Plan Flow (High)

- **Target**: `tests/integration/` (e.g. `test_plan_creation_workflow_compliance.py` or new `test_structured_plan_tools.py`).
- **Change**: Add tests that (1) call `create_plan` with minimal content and assert file exists under plans dir; (2) call `register_plan_in_roadmap` and assert roadmap contains new entry and existing entries unchanged; (3) optionally run a simulated create-plan sequence (create_plan + register_plan_in_roadmap) and verify both plan file and roadmap. Use fixtures or temp structure to avoid mutating real roadmap in CI.

### Step 7: Update Roadmap and Memory Bank (High)

- After implementation and tests pass, add this plan to roadmap (e.g. "Structured plan creation via Cortex MCP tools — COMPLETE") and update progress/activeContext per project workflow.

## Dependencies

- **Cortex MCP**: Existing `get_structure_info`, `manage_file`; structure and memory-bank services.
- **Synapse**: Create-plan prompt and agents; path resolution and roadmap format must stay aligned with tool behavior.

## Success Criteria

- `create_plan` MCP tool exists: accepts title and content (or sections), writes plan file under plans directory with correct path resolution and safe filename.
- `register_plan_in_roadmap` MCP tool exists: accepts plan title, description, status, section; updates roadmap by merging one entry without truncating others; uses memory-bank write path.
- Create-plan prompt instructs agents to use these tools first, with fallback to current manual flow.
- All new code has unit tests; integration tests cover tool behavior and optional create-plan flow. Coverage target: 95% for new code; project minimum 90% maintained.
- Documentation (docs/api/tools.md, CLAUDE.md) describes the new tools.

## Testing Strategy

- **Coverage target**: Minimum 95% for new plan-operation code; maintain project-wide ≥90%.
- **Unit tests**: Test path resolution, slug sanitization, plan file write, roadmap parse/merge/format (no traversal, no corruption of other entries). AAA pattern; no blanket skips.
- **Integration tests**: Call `create_plan` and `register_plan_in_roadmap` via MCP (or test helpers that invoke same logic); assert file system and roadmap state. Use isolated dir or fixture for roadmap if needed.
- **Regression**: Existing plan-creation workflow compliance tests (Phase 66) still pass; if prompt changes add a "prefer tools" path, add test that prompt mentions the new tools.

## Risks & Mitigation

- **Roadmap format drift**: Parsing and merging depend on current roadmap format (headers, list items). Mitigation: Keep merge logic simple (e.g. section-based insert); add tests with sample roadmap snippets; document expected format.
- **Backward compatibility**: Agents or clients that only have `manage_file` and Write must still be able to create plans. Mitigation: Fallback remains in prompt; no removal of existing capabilities.

## Notes

- This plan does **not** remove `manage_file` or the requirement that roadmap lives in memory bank; it adds a **structured** layer on top so the agent rarely handles full roadmap content.
- Phase 66 (plan creation workflow compliance) remains in force; the new tools should satisfy the same constraints (path from structure_info, roadmap updates via memory-bank write) inside the tool implementation.
